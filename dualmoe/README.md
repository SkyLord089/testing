# DualMoE v0.6.2 — «Разгон»: до 3× токенов без потери качества + авто-бюджет памяти

Декод ускорен **спекулятивным разгоном**: движок сам пишет черновик продолжения по истории токенов и проверяет его **одним графом**, принимая только то, что модель подтвердила. Текст ответа **побитово совпадает** с обычным жадным декодом (это проверяет Gate 9), но на один граф приходится 2–7 токенов вместо одного. Таблица черновиков сохраняется на диск рядом с моделью (`.spec`), поэтому разгон работает уже с первого ответа после перезапуска; если модель отклоняет черновики, защита автоматически возвращает обычный декод.

| Замер (демо-модель, CPU, 4 потока) | tok/s |
| --- | --- |
| Обычный декод (`Разгон = 0`) | 6.5 |
| `Разгон = 6` | 21.1 |
| `Разгон = 8` | 116.3 |

Настройка — ползунок **«Разгон (черновиков на граф)»** (0 = выключено) и поле `spec_tokens` в `POST /api/model/load`. В телеметрии появились **«Разгон (токенов на граф)»** и **«Черновики / принято»**.

Один самодостаточный исполняемый файл **`DualMoE.exe`** для Windows 10/11 x64: запуск двойным кликом открывает **отдельное окно DualMoE** (Edge WebView2, своя иконка в панели задач, без вкладок и адресной строки). Внутри — тот же движок `VRAM ⇄ RAM (0 чтений HDD)`, `GPU Vulkan ∥ CPU AVX2` и интерфейс **LearnHarness × Hermes Agent (Nous Research)**, оптимизированный под **Ryzen 7 5700X + 16 ГБ DDR4 + Radeon RX 580 8 ГБ Vulkan + HDD + Windows 11**.

## Benchmark: автоподбор максимально быстрых параметров

Вкладка **Benchmark** в приложении (или `POST /api/bench/start`) подбирает параметры под конкретное железо:

| Режим | Что делает | Цена |
| --- | --- | --- |
| **Быстрый расчёт** | Читает GGUF-метаданные + свободные VRAM/RAM, считает KV-кэш с учётом SWA и разделяемых слоёв, банк экспертов, арену DDR4, микробатч и потоки; объясняет каждое число | мгновенно |
| **Полный замер** | Перебирает кандидатов (потоки `физические / SMT / половина`, доля `CPU ∥ GPU`, банк VRAM `65% / 100%`, микробатч `16 / 32`), для каждого перезагружает модель и меряет реальные `tok/s`, `TTFT`, попадания в VRAM и чтения HDD | 1 перезагрузка на кандидата |

Победитель выбирается по score `tok/s × VRAM-hit − диск`, оставляется загруженным, а кнопка **«Применить»** доступна и позже (в т.ч. для любого другого кандидата).

API:

```bash
curl -X POST localhost:8090/api/bench/start  -d '{"mode":"full","tokens":96,"max_candidates":12}'
curl      localhost:8090/api/bench/status
curl -X POST localhost:8090/api/bench/apply  -d '{"index":3}'
curl -X POST localhost:8090/api/bench/cancel
```

## Что нового в v0.6.2

Раньше бюджет памяти задавался руками: ползунки «Банк в VRAM» и «Арена DDR4» надо было угадывать, а загрузчик лишь подрезал слишком смелые числа. Теперь бюджет считает движок — по одному правилу и в загрузчике, и в Benchmark, и в UI.

* **Приоритет памяти зашит: VRAM → ОЗУ → HDD.** Сначала всё, что влезает в видеопамять (банк экспертов), затем ОЗУ под остальных экспертов на CPU, и только то, что не влезло ни туда, ни туда, читается с диска.
* **Два резерва, которые вы задаёте.** «Оставить системе VRAM» и «Оставить системе ОЗУ»: сколько памяти не отдавать модели. `−1` = авто (VRAM: 5% + 256 МБ, ОЗУ: 10% + 1 ГБ), `0` = забирать всё. Резерв вычитается из **свободной** памяти, поэтому открытый браузер учитывается сам.
* **Живое превью до загрузки.** `GET /api/budget` считает раскладку по заголовку GGUF, не занимая ни байта: в панели движка сразу видно «VRAM-банк … (N экспертов) · ОЗУ … (M) · диск …» и «в памяти X% модели». Двигаете ползунок — цифры меняются.
* **Честная статистика размещения.** Телеметрия показывает `expert_total_mb`, `expert_in_vram_mb`, `expert_in_ram_mb`, `expert_on_disk_mb` и число слотов экспертов — это измерение по арене и банку, а не оценка. В UI: строка **«Эксперты: VRAM / ОЗУ / диск»**.
* **Шаг — целый эксперт, а не мегабайт.** Бюджет выравнивается по размеру одного эксперта слоя, поэтому на маленькой модели эксперт не «округляется» в ноль и не уезжает на диск.
* **Пересчёт после OOM-повтора.** Если модель пришлось перезагрузить с меньшим числом GPU-слоёв, бюджет VRAM пересчитывается под реально размещённые слои, а не под изначально запрошенные.
* **Benchmark считает тем же кодом.** План в Benchmark и загрузка модели используют один и тот же `plan_auto_budget`, так что обещанные числа совпадают с фактическими.
* **Gate 11** проверяет: VRAM заполняется первой, резервы соблюдаются, явные резервы уважаются, авто-резерв масштабируется с объёмом памяти, а модель, которая целиком влезает, заканчивает загрузку со 100% в памяти.

## Что нового в v0.6.1

«Параллельный режим GPU ∥ CPU» был надписью: движок включал CPU только тогда, когда банк экспертов в VRAM уже **полон** (`n_filled == n_slots`), поэтому на модели, которая в банк влезает целиком, 100% работы делал GPU, а счётчик «CPU-экспертов» показывал… размер маршрута (`n_expert_used`), то есть статистику маршрутизации, а не работу CPU. Теперь это измеримо и включается руками.

* **Форсированный шов GPU ∥ CPU.** Новый параметр `parallel_seam_share` (ползунок **«GPU ∥ CPU на одном токене»**, 0…60%) отдаёт заданную долю экспертов каждого слоя процессору **даже при свободных слотах банка**: слот освобождается, GPU-часть того же слоя становится меньше, и оба движка считают **один и тот же токен** одновременно.
* **Честное измерение.** Планировщик ggml пишет таймлайн каждого сплита декод-графа; `llama_moe_cache_parallel_profile()` сводит его в `par_layers_dual` (слои, где GPU- и CPU-сплит **пересекались во времени**), `par_layers_serial`, `par_gpu_ms` / `par_cpu_ms` и `par_overlap_pct`. В панели «Телеметрия» — строка **«GPU ∥ CPU (слоёв вместе / порознь)»**: `0 / 0` значит, что параллельной работы не было (и приложение так и говорит, а не рисует красивое число).
* **`GET /api/seam?cpu_share=0.9&tokens=32`** — проверка на живой модели без перезагрузки: применяет долю, генерирует ответ и возвращает `dual_layers`, `serial_layers`, `gpu_ms_per_token`, `cpu_ms_per_token`, `overlap_pct`.
* **Benchmark меряет и шов.** Новый дешёвый перебор `seam = 0 / 0.15 / 0.30 / 0.45` (без перезагрузки): если CPU-половина тормозит токен, ноль остаётся победителем и шов не включается.
* **Счётчик «CPU-экспертов» больше не врёт**: он больше не пополняется на маршрутизации; реальные числа приходят из событий кэша (`n_cpu`).
* **Исправлено `apply_live_config`**: если загрузка урезала банк VRAM под свободную память, живая смена потоков / доли / шва больше не отваливалась с «Эти параметры требуют перезагрузки модели».
* **Gate 10** проверяет, что шов применяется, ограничивается 0…0.9, выключается на живом контексте и что без GPU приложение показывает `0` слоёв параллелизма вместо выдуманных чисел.

> Честное ограничение: в среде сборки нет GPU, поэтому сам `par_layers_dual > 0` проверяется только на реальной Vulkan-карте (RX 580). На CPU-only прогоне шов выключен, и это видно в телеметрии.

## Что нового в v0.6.0

* **Спекулятивный «Разгон» декода.** n-граммный драфтер (2..4 токена контекста → эмпирическое распределение следующего токена) строит черновик по истории токенов; батч `[следующий токен, черновики…]` проверяется **одним графом**, подтверждённый префикс остаётся в KV-кэше, отклонённый — откатывается (`llama_memory_seq_rm`). Один граф отдаёт `1 + принято` токенов.
* **Побитовая идентичность.** Ячейка `bonus` берётся из строки логарифмов **последней подтверждённой** позиции, поэтому отклонённые черновики не влияют на выбор; Gate 9 сравнивает ответ с обычным декодом во всех четырёх конфигурациях (потоки 1/2, с потоковыми экспертами и без).
* **Самопроверка выгоды.** Если на граф выходит меньше ~1.1 токена, разгон выключается на этот ответ — на «сложной» модели не бывает медленнее обычного декода.
* **Кэш на диск.** Таблица разгона (`*.gguf.spec`, magic `DMSPEC01`) пишется вместе с горячим кэшем экспертов и загружается при старте: первый ответ после перезапуска на демо-модели ускорился с 9.1 до 12.3 tok/s, коэффициент — с 1.82 до 2.41.
* **Короче прогрев.** Набор горячих экспертов сначала считывается с диска последовательно и загружается в банк VRAM в порядке маршрута, а не «вслепую» — первый токен уже тёплый; в лог пишется `[load] прогрев VRAM-банка: … МБ за … мс`.
* **Телеметрия и UI.** Новые поля `spec_tokens`, `spec_drafted`, `spec_accepted`, `spec_efficiency` в `/api/status`; в панели «Телеметрия» — коэффициент разгона и счётчик черновиков.
* **Gate 9**: разгон не меняет ответ, реально принимает черновики, переживает перезагрузку таблицы с диска и отключается, когда невыгоден.

## Что нового в v0.5.2

* **Исправлена ошибка загрузки `Пробный прогон захвата графа вернул код 2`** (в логе: `ggml_backend_sched_graph_compute_async failed with error 1` → `llama_decode: failed to decode, ret = 2`). Причина: `ret = 2` — это `GGML_STATUS_ABORTED`, граф прерывался не из-за нехватки памяти, а из-за **устаревшего флага отмены**. ggml проверяет `abort_callback` после каждой ноды, поэтому флаг, поднятый кнопкой «Стоп», отменённым бенчмарком или выгрузкой предыдущей модели, убивал **следующий** граф — включая пробный 1-токенный прогон, из-за чего арена экспертов оставалась непривязанной.
  * Флаг теперь «разоружается»: отмена, поднятая вне графа, сбрасывается на первой же проверке (свежая отмена в пределах 400 мс всё равно срабатывает, так что «Стоп» во время ответа работает как раньше).
  * Пробный прогон захвата графа всегда стартует с чистым состоянием отмены.
  * Если пробный прогон всё же не удался (например, реально не хватило VRAM), загрузка **не падает**: модель поднимается в деградированном режиме со стримингом экспертов, понятным предупреждением и подсказкой.
  * Прерванный граф больше не пишется в отчёт о падении (раньше следующий старт показывал ложный баннер «модель упала»).
* **Новый Gate 8** в тестах воспроизводит именно этот сценарий (отмена → загрузка; задержанная отмена; отмена во время генерации; работа после прерванного хода) и падает, если фикс откатить.

## Что нового в v0.5.1

* **Быстрый полный замер.** Потоки и доля `CPU ∥ GPU` применяются к живому контексту (`apply_live_config`) — перезагрузка модели остаётся только для банка VRAM и микробатча; перебор идёт «3 точки → уточнение вокруг победителя», отсюда ~60× ускорение на демо-модели.
* **Горячий кэш экспертов между запусками** — файл `*.gguf.warm` рядом с моделью; при старте набор закрепляется, первый ответ не учится заново.
* **Класс статических экспертов** — 25–40% банка VRAM резервируется под структуру и системный промпт, смена темы их не выбивает.
* **Префетч по маршруту промпта**, а не только по предыдущему токену.

## Benchmark: как устроен перебор

| Ось | Как меряется | Цена |
| --- | --- | --- |
| Потоки CPU | `llama_set_n_threads` на живом контексте | 1 генерация |
| Доля `CPU ∥ GPU` | `llama_set_moe_cache_cpu_share` | 1 генерация |
| Шов `GPU ∥ CPU` (один токен) | `llama_set_moe_cache_forced_seam` | 1 генерация |
| Банк VRAM / микробатч | только перезагрузкой модели | полная загрузка |

Кривая по каждому дешёвому параметру снимается в 3 точках, затем уточняется только интервал вокруг лидера — победитель не теряется, а время не тратится на заведомо плохие значения.

## Сборка

```bash
# нативное окно (Windows x64, MSVC + Ninja, статический CRT)
cmake -S dualmoe -B build-win -G "Ninja Multi-Config" \
      -DCMAKE_TOOLCHAIN_FILE=$PWD/dualmoe/cmake/x64-windows-msvc.cmake \
      -DLLAMA_SOURCE_DIR=C:/llama-cpp -DGGML_VULKAN=ON -DDUALMOE_DESKTOP_WINDOW=ON
cmake --build build-win --config Release --target DualMoE

# консольный сервер (любая ОС)
cmake --build build-win --config Release --target dualmoe-server
```

Иконка пересобирается скриптом `scripts/make_icon.py` (Pillow) из `assets/icon_source.png`.

## Ключевые возможности движка (v0.3.0+ / актуально в v0.6.2)

1. **Режим «Без HDD» (`100% в VRAM + RAM` / 0 обращений к диску во время чата):**
   - Однопроходный линейный предзагрузчик (`FILE_FLAG_SEQUENTIAL_SCAN`, блоки по `16 МБ` по возрастанию смещения на диске) читает модель с механического HDD один раз при старте без рывков головок.
   - При объёме экспертов больше свободной ОЗУ (модели `12–18 ГБ` на ПК с `16 ГБ DDR4 + 8 ГБ RX 580`) автоматически активируется **раздельный обмен `VRAM ⊕ RAM` (`Disjoint Swap`)**: части, хранящиеся в `VRAM`, освобождают свои страницы в `DDR4` (`MEM_DECOMMIT`), экономя до `5 ГБ ОЗУ` и не допуская свопинга Windows в `pagefile.sys` на HDD.
   - Для плотных моделей (`Dense`) используется линейная загрузка `LLAMA_LOAD_MODE_NONE` напрямую в `VRAM + ОЗУ` без страничных промахов на HDD.
2. **Максимальная параллельная нагрузка `GPU ∥ CPU` + Живой обмен `RAM ⇄ VRAM`:**
   - Полный предварительный прогрев слотов банка `VRAM` (`llama_moe_cache_prewarm`) до первого токена.
   - Замкнутый авто-балансировщик с гистерезисом частоты `CRF`: разовые промахи считаются параллельно на ядрах Ryzen 7 5700X по AVX2/FMA из `DDR4`, а реально часто запрашиваемые блоки автоматически поднимаются **`RAM → VRAM`**, вытесняя остывшие слоты обратно **`VRAM → RAM`**.
3. **8-этапный Инспектор загрузки и сбоев + Защита RX 580 / 16 ГБ RAM:**
   - `uBatch <= 32` Guard, `fits_max_buf` Vulkan Guard, защита проекций драйвера AMD Adrenalin, синхронный лог `dualmoe-load.log` и Windows SEH Crash Forensics (`dualmoe-crash.txt`).
4. **Интерфейс LearnHarness × Hermes Agent + OpenAI API:**
   - 3 палитры (**Graphite**, **Nous Cobalt**, **Paper**), встроенный обзор дисков (`C:\`, `D:\`, `E:\`...), живая телеметрия `VRAM ⇄ RAM` и полная совместимость с **LearnHarness** (`http://127.0.0.1:8090/v1`, Model ID: `dualmoe-default`).

## Запуск на Windows 11

1. Скачайте единственный файл **`DualMoE.exe`** со страницы **GitHub Releases (`dualmoe-v0.6.2`)**.
2. Двойной клик — открывается отдельное окно DualMoE (профиль «HDD-Турбо: VRAM ⇄ RAM» включён по умолчанию).
3. В левой панели нажмите **«Файл модели…»**, выберите `.gguf` и нажмите **«Загрузить модель»**.

Модель можно передать сразу: `DualMoE.exe --model D:\Models\gemma-4-26b-a4b.gguf`.
