# План: с 5.7.1/6.2.4 + 2.2.1 → HIP 6.4 + torch 2.7

Правило: **не переходить на следующий этап, не закрыв критерий выхода предыдущего.** Иначе будем чинить сразу пять проблем и не поймём, что помогло.

---

## Этап 0. Базовая линия (сейчас)

**Цель:** знать, что система вообще жива и что именно видит HIP.

1. `scripts/preflight.ps1` → `preflight-report.txt`.
2. `hipInfo.exe` из 6.4 и из 6.2 — сравнить.
3. Зафиксировать версии драйвера, HIP, torch, ZLUDA, Python.
4. Записать в `07-tracker.md` строку «Baseline».

**Выход:** `preflight-report.txt` есть, в нём `gfx803` найден хотя бы в 6.2.

> Если **6.4 не видит карту вообще** — не тратим время на torch. Сначала `01-diagnosis.md#1` (драйвер / HIP_VISIBLE_DEVICES / порядок PATH / единственная версия HIP).

## Этап 1. rocBLAS с ядрами gfx803 под 6.4

**Цель:** `rocBLAS` в 6.4 умеет GEMM для gfx803 без ошибок и без мусора.

Варианты (по возрастанию трудозатрат) — детали в `05-gfx803-rocblas.md`:

- **A. Взять готовый community-набор для 6.4**, если он появился (список источников — в `02-matrix.md`). Это самый быстрый путь; проверить дату и наличие `gfx803` в имени файлов ядер.
- **B. Позаимствовать Tensile-ядра gfx803 из 6.2.4** и подложить в `6.4\bin\rocblas\library`, оставив `rocblas.dll` от 6.4. Работает не всегда: ABI/Tensile версии между 6.2 и 6.4 могут не совпасть → тогда ошибка `Cannot read ...` или «no kernel found».
- **C. Собрать rocBLAS/Tensile для gfx803 из исходников 6.4** с логиками Tensile от Polaris (см. `05`, там же ссылки на готовые Docker-сборки и YAML-логики).

**Выход:** `rocblas-test --gtest_filter=*gemm*` или минимальный тест GEMM из `verify-torch27.py` проходит, **и** сверка с CPU (double precision) даёт ошибку < 1e-2 для fp16 и < 1e-4 для fp32.

## Этап 2. ZLUDA + torch 2.7: устройство видно, GEMM идёт

1. ZLUDA **3.9.6 `ZLUDA-windows-amd64.zip`** (собран под HIP 6.x; для 7.1 — тот же архив).
2. Подмена DLL: `scripts/patch-torch-zluda.ps1` (делает бэкап и проверяет, что источник/цель одного бита).
3. `DISABLE_ADDMM_CUDA_LT=1` — обязательно.
4. `scripts/verify-torch27.py` — по секциям.

**Выход:** в `verify-torch27.py` зелёные секции `basic`, `gemm`, `conv`, `attention`; `accuracy` в пределах допуска.

> Если падает только `cublasLt`-секция → идём в `06-torch27.md#1` (там три разных способа погасить cublasLt-путь, включая пересборку `cublasLt.dll`).
> Если падает `rocBLAS`-секция → возвращаемся на этап 1.

## Этап 3. ComfyUI: первый кадр

1. `scripts/comfyui-user.bat` (или добавить аргументы в свой): `--disable-async-offload --disable-pinned-memory --use-quad-cross-attention --reserve-vram 0.9`.
2. Проверить, что `comfy\zluda.py` от текущей версии репозитория (в `comfyui-n.bat` он копируется из `comfy\customzluda\zluda.py`).
3. Тест: SD1.5 512×512, 20 шагов, fp16. Затем SDXL 1024×1024 (может потребовать `--lowvram`).

**Выход:** картинка без артефактов, повторяемая при том же seed (сравнить 2 прогона).

## Этап 4. Стабилизация и производительность

- Кэш ZLUDA (`ZLUDA_CACHE_DIR`), чтобы не компилировать каждый раз.
- Проверить, не «съедает» ли fp32-путь скорость: на gfx803 fp16 быстрее, но следить за качеством.
- Отдельно проверить VAE decode (tiled VAE / TinyVAE при 8 ГБ).
- Зафиксировать рабочую комбинацию в `07-tracker.md` как «known good» и сделать бэкап `venv\torch\lib` + `zluda\`.
